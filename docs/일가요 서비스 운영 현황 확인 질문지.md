각 질문 아래에 현재 구현된 방식이나 앞으로 적용할 방식을 작성해 주세요.

## 1. 백그라운드 위치정보 수집 여부

외근을 시작한 이후 앱이 백그라운드 상태에서도 이용자의 위치정보를 계속 수집하나요?

### 확인할 사항

* 다른 앱을 사용하는 동안에도 위치정보를 수집하는지
* 휴대전화 화면이 꺼진 상태에서도 위치정보를 수집하는지
* 앱이 백그라운드에 있는 동안에도 위치정보를 수집하는지
* 외근 종료 버튼을 누를 때까지 위치정보를 계속 수집하는지
* 앱을 완전히 종료하면 위치정보 수집도 종료되는지

### 현재 서비스 방식

> 답변: **모든 항목 "아니오". 백그라운드 위치 수집은 전혀 없습니다.**
>
> 위치정보는 **앱 화면이 켜져 있는 동안(포그라운드)에만, 그 순간의 좌표 1회**만 조회합니다.
> 지속 추적·이동 경로 기록은 기능 자체가 존재하지 않습니다.
>
> **근거 (코드·설정)**
>
> * 권한 선언이 포그라운드 전용 — Android `ACCESS_COARSE/FINE_LOCATION` 만 선언, **`ACCESS_BACKGROUND_LOCATION` 없음**. iOS 는 `NSLocationWhenInUseUsageDescription` 만 있고 `Always` 계열 키 없음 (`app.json:31-34`, `52-71`)
> * 백그라운드 실행 인프라 부재 — `expo-task-manager`·`expo-background-fetch` 의존성 없음, `startLocationUpdatesAsync`·`watchPositionAsync`·headless task 코드 0건
> * 위치 획득 경로가 단 하나이며 1회성 — `requestForegroundPermissionsAsync()` → `getCurrentPositionAsync()` (`src/utils/geolocation.ts:11-24`)
>
> **위치를 조회하는 시점 (전부 5곳, 모두 포그라운드)**
>
> | 위치 | 시점 | 목적 |
> |---|---|---|
> | `src/components/MapDashboard.tsx:140` | 지도 화면 진입 시 1회 | 지도 '내 위치' 표시 |
> | `app/(tabs)/trips/navigate.tsx:37` | 길안내 화면 진입 시 1회 | 내 위치 점 표시 |
> | `app/(tabs)/fields/new.tsx:208` | 사용자가 "현재 위치" 버튼을 누를 때 | 현장 좌표 입력 |
> | `app/(tabs)/fields/[id]/edit.tsx:206` | 사용자가 "현재 위치" 버튼을 누를 때 | 현장 좌표 수정 |
> | `src/components/fields/useQuickPhoto.ts:80` | 사용자가 빠른 촬영을 누를 때 | 100m 내 현장 자동 매칭 |
>
> **외근 기능은 위치와 무관합니다** (약관 문구 작성 시 중요)
>
> * 외근 시작 `POST /api/trips/start` 전송 항목 = 제목 + 방문 예정 현장 ID·순서. 위치 좌표를 보내지 않음 (`src/api/endpoints/trips.ts:19-23`)
> * 현장 체크인 `POST /api/visits/check-in` 전송 항목 = `fieldId` 하나뿐 (`src/stores/visitStore.ts:74`)
> * 경로 최적화·실도로 경로의 출발 좌표도 GPS 가 아니라 **직전 방문 현장의 좌표** (`app/(tabs)/trips/active.tsx:380-383`)
> * 백엔드 API 목록에 geofence 엔드포인트가 남아 있으나(구버전 잔존) **앱은 호출하지 않음**
>
> **권한 거부 시**: 오류 없이 기본 동작으로 폴백 (지도는 기본 중심 표시, 빠른 촬영은 수동 현장 선택).
> **앱 종료 시**: 애초에 백그라운드 수집이 없으므로 수집도 함께 종료.

## 2. 위치기록 보관기간

외근 중 수집한 위도, 경도, 이동 경로 등의 위치기록을 외근 종료 후 얼마 동안 보관하나요?

### 가능한 운영 방식 예시

* 외근 종료 즉시 삭제
* 외근 종료 후 30일간 보관 후 자동 삭제
* 외근 종료 후 1년간 보관 후 자동 삭제
* 사용자가 삭제할 때까지 보관
* 관리자가 삭제할 때까지 보관
* 외근기록을 삭제할 때 위치기록도 함께 삭제
* 회원 탈퇴 시 삭제

### 현재 서비스 방식

> 답변: **해당 없음 — "이용자의 위치기록"이라는 데이터가 존재하지 않습니다.**
>
> 이동 경로·위경도 로그를 저장하는 저장소도, 서버로 전송하는 경로도 없습니다.
> 조회한 좌표는 화면 표시·거리 계산에 쓰이고 앱 메모리에서 사라집니다.
>
> **단 하나의 예외** — 사용자가 현장 등록/수정 화면에서 **"현재 위치" 버튼을 직접 누르고 저장**하면,
> 그 좌표가 **현장(장소)의 좌표 속성**으로 서버에 저장됩니다.
> 이는 이용자의 위치이력이 아니라 **현장 마스터 데이터**이며, 3항의 현장·외근기록 보관 정책을 따릅니다.
>
> **약관 권장 문구**: "서비스는 이용자의 이동 경로 및 위치이력을 수집·보관하지 않습니다.
> 위치정보는 이용자가 앱을 사용하는 시점에 일시적으로 이용되며 별도로 저장되지 않습니다."

### 자동 삭제 기능 구현 여부

> 답변: **해당 없음** (삭제 대상이 되는 위치기록 자체가 없음).

## 3. 외근기록 보관기간

방문 장소, 외근 시작·종료 시간, 업무내용, 업무보고 등의 외근기록을 얼마 동안 보관하나요?

### 가능한 운영 방식 예시

* 사용자가 삭제할 때까지 보관
* 관리자가 삭제할 때까지 보관
* 회원 탈퇴 시까지 보관
* 외근 종료 후 일정 기간 보관 후 자동 삭제
* 조직 또는 관리자가 정한 기간 동안 보관
* 별도의 삭제 없이 계속 보관

### 현재 서비스 방식

> 답변: **사용자가 직접 삭제할 때까지 보관. 기간 만료에 따른 자동 삭제는 없습니다.**
>
> 사용자가 앱에서 직접 삭제할 수 있는 항목 — 외근(`DELETE /api/trips/{tripId}`),
> 보고서(`DELETE /api/reports/{reportId}`), 현장(`DELETE /api/fields/{fieldId}`),
> 현장 메모·사진(`DELETE .../memos/{memoId}`, `.../photos/{photoId}`).
>
> 보관기간 만료 후 일괄 삭제하는 배치 작업은 API 목록·프론트 어디에도 근거가 없습니다.
> **[백엔드 확인 필요]** 서버측 정리 배치가 실제로 존재하는지 확인 후 확정.

### 위치기록과 외근기록의 보관기간이 다른지

> 답변: **해당 없음** — 별도 보관되는 위치기록이 없으므로 비교 대상이 없습니다(2항 참조).

## 4. 개인정보 삭제 방식

회원 탈퇴 또는 개인정보 삭제 요청이 접수되면 개인정보를 어떤 방식으로 삭제하나요?

### 확인할 사항

* 회원정보를 데이터베이스에서 즉시 삭제하는지
* 일정 기간 보관한 후 삭제하는지
* 개인정보를 완전히 삭제하는지
* 개인을 식별할 수 없도록 익명화하는지
* 외근기록과 위치기록도 함께 삭제하는지
* 백업 데이터에 저장된 개인정보도 삭제하는지
* 법령상 보관이 필요한 정보만 별도로 분리하여 보관하는지

### 현재 서비스 방식

> 답변: **자동화된 삭제 절차가 없습니다 — 운영팀 이메일 접수 후 수동 처리.**
>
> 백엔드 API 전체(82개 경로)에 **회원 삭제 엔드포인트가 존재하지 않습니다**
> (`DELETE /api/me` 계열 부재). 사용자 계정 관련 API 는 조회(`GET /api/me`),
> 이름 변경(`PATCH /api/me`), 비밀번호 변경(`PATCH /api/me/password`) 뿐입니다.
>
> **[백엔드 확인 필요]** 아래는 백엔드/운영 담당이 확정해야 하는 항목입니다.
>
> * DB 즉시 삭제인지 / 익명화인지
> * 외근·방문·보고서·현장·사진까지 연쇄 삭제되는지
> * 법령상 보관 항목의 분리 보관 여부

### 삭제 처리에 걸리는 기간

> 답변: **[운영 결정 필요]** — 수동 처리이므로 목표 처리기한을 정해야 합니다(예: 요청 접수 후 영업일 기준 7일 이내).

### 백업 데이터 처리 방식

> 답변: **[백엔드 확인 필요]** — 백업 운영 여부·보관주기·백업본 내 개인정보 파기 방식 미확인.

## 8. 비밀번호 암호화 저장 여부

회원의 비밀번호를 데이터베이스에 어떤 방식으로 저장하나요?

### 가능한 방식 예시

* bcrypt 해시 적용
* Argon2 해시 적용
* Spring Security `PasswordEncoder` 적용
* Firebase Authentication 사용
* 자체 로그인 없이 소셜 로그인만 사용
* SHA-256 등 단방향 해시 적용
* 암호화 없이 평문으로 저장
* 아직 회원가입 기능이 구현되지 않음

### 현재 서비스 방식

> 답변: **[백엔드 확인 필요] — 해시 저장으로 알려져 있으나 알고리즘 미확인.**
>
> 프론트는 HTTPS 로 비밀번호를 전송할 뿐 저장 방식에 관여하지 않습니다.
> 현재 서비스 중인 개인정보처리방침 1조에는 이미 "비밀번호(해시 저장)"로 명시되어 있으므로,
> **백엔드 담당에게 알고리즘(bcrypt / Argon2 등)만 확인받아 채우면 됩니다.**
>
> 정황 근거: 서버가 비밀번호 정책을 검증합니다(`password_policy_violation` 에러 코드),
> 비밀번호 변경은 현재 비밀번호 확인을 거칩니다(`current_password_invalid`).

### 사용 중인 인증 기술 또는 라이브러리

> 답변: **JWT Bearer 토큰 기반 자체 인증** (액세스 토큰 + 리프레시 토큰 + 세션 ID).
> 소셜 로그인·Firebase 미사용. 서버측 해시 라이브러리는 **[백엔드 확인 필요]**.

### 비밀번호 원문 확인 가능 여부

* [x] 운영자도 비밀번호 원문을 확인할 수 없음 *(해시 저장 전제 — 8항 확인 후 확정)*
* [ ] 데이터베이스에서 비밀번호 원문을 확인할 수 있음
* [ ] 확인 필요
