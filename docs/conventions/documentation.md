# 문서 규칙

> **확정**: 2026-10-17. docs 는 **우리가 일하는 방식과 같은 모양**이어야 한다 — 일 하나의 기획·설계·결과는
> 한 폴더에 모이고, 모든 일에 걸리는 규칙만 따로 둔다.

## 1. 어느 폴더에 넣나

위에서부터 묻고, **처음 "예"가 나오는 곳**에 넣는다.

| 순서 | 질문 | 예 → |
|---|---|---|
| 1 | 외부 사람(학교·심사·발표 청중)에게 **보여주려고** 만든 결과물인가? | `deliverables/` |
| 2 | 특정 일이 아니라 **모든 일에 적용되는 규칙**인가? | `conventions/` |
| 3 | **앱 코드를 바꾸는 일**에 속하나? | `features/<일>/` |
| 4 | 그 밖 — 백엔드 협업·출시·장애처럼 앱 밖의 일 | `operations/` |

1·2 는 **문서의 용도**, 3·4 는 **일의 종류**를 묻는다. 순서는 겹침을 감추려는 게 아니라 이 두 층을 나눈 것이다.

### 경계 판정 사례

| 문서 | 판정 | 근거 |
|---|---|---|
| 디자인 시스템 | conventions | 모든 화면에 적용되는 규칙. 어떤 일이 토큰을 바꾸면 그 기획은 그 일의 폴더에 두고 링크한다 |
| 백엔드 전달본 | operations/backend | 받는 사람이 백엔드이고 큐는 backlog 하나. 기능 폴더에서는 링크만 |
| Claude 세션 간 구현 인수인계 | features/<일> | 그 일의 일부 |
| 출시 체크리스트 | operations/release | 체크리스트 자체는 출시 업무. 그 안의 개발 항목은 각 기능 폴더로 |
| 주간보고 | deliverables | 내용은 기능 진척이지만 용도가 외부 보고 |
| ERD | operations/backend | 진실 출처가 백엔드 스키마이고 협업에 쓴다 |
| IAD | features/ 입구 | 기능 전체의 지도 |

## 2. 기능 폴더 안

```
features/<일>/
  README.md      주 문서. 머리에 상태(아래)를 적는다
  *.md           같은 일의 다른 문서 (요구사항·설계·인수인계 등)
  archive/       더 이상 고치지 않는 스냅샷
```

- **폴더 하나 = 일 하나.** 브랜치·로드맵 항목과 같은 단위다. 이름은 kebab-case.
- 상태: `검토`(방향만) → `확정`(착수 대기) → `착수`(개발 중) → `구현 완료`(배포됨).
- 구현이 끝나도 **폴더를 옮기지 않는다.** 상태만 `구현 완료`로 닫는다. 그 일의 기획과 결과가 계속 한곳에 있어야 한다.
- 작업 순서는 파일명 번호가 아니라 [`features/README.md`](../features/README.md) 의 표가 관리한다.

## 3. archive

- `archive/` 는 **각 폴더 안**에 둔다. 최상위 archive 는 없다 — 끝난 문서도 자기 일 옆에 있어야 찾는다.
- archive 문서는 고치지 않는다. 링크가 깨지는 경우만 예외.

## 4. 문서가 아닌 것

- Claude 스킬(`SKILL.md`)은 `.claude/skills/` 에 둔다. docs 에 두지 않는다.
- 결과물(영상·스크린샷)을 `.gitignore` 대상 폴더(`docs/tmp/`·`docs/presentation/`)에 두지 않는다 — 사라진다.
- 저장소가 **공개**다. 계정 비밀번호는 추적 문서에 적지 않는다 (`docs/tmp/` 에만).
