## 1. 🟠 §34 — TLS 자동 갱신이 실제로 걸렸는가 (기한: 11/2 만료 전)

8/3 장애(§33, 인증서 만료로 전면 불통)는 재발급으로 복구됐다. 그런데 **재발 방지(자동 갱신)가 적용됐는지는
밖에서 볼 수 없다.**

- 2026-10-01 실측: `notBefore=2026-08-04` · `notAfter=2026-11-02` · `Let's Encrypt YE1`.
- certbot 은 만료 30일 전(≈10/3)부터 갱신을 시도한다. **10월 둘째 주에도 `notBefore` 가 8/4 면 자동 갱신이
  안 돌고 있다** — 8월과 똑같이 11/2 에 앱 전체가 멈춘다.

**요청**: 아래 중 하나로 답해 달라.
- "DNS-01 자동화(`certbot-dns-cloudflare` 등) + deploy-hook(nginx/컨테이너 reload) 적용함" — 또는
- `sudo certbot renew --dry-run` 결과 한 줄.

8월 원인은 `--manual` 발급이라 `certbot.timer` 가 90일 내내 **조용히 건너뛴** 것이었다. 같은 상태면
dry-run 이 실패한다.

## 2. 🟠 §36 — 방문 삭제 `DELETE /api/visits/:id`

명세 v2: 외근 정리 화면에서 방문 카드를 **스와이프 삭제**, 방문 수정 화면의 **`방문 삭제`** 버튼.
**현장(마스터)은 남기고 그 방문과 첨부만** 지운다.

**실측**: `DELETE /api/visits/:id`, `DELETE /api/trips/:tripId/visits/:id`, `PATCH /api/visits/:id` 모두 라우트 없음.

**요청**
1. `DELETE /api/visits/:id` → 204. 방문 사진·메모 cascade(스토리지 객체 포함).
2. 그 목적지(`trip_destinations`)는 **`pending` 으로 되돌릴지 `skipped` 로 둘지** 정해서 알려 달라 — 프론트가 맞춘다.
3. 그 방문이 보고서의 현장 보고에 쓰였으면 **409 `visit_in_report`** (→ 8번 §39 와 같은 판정).

**프론트 현황**: UI(스와이프·버튼·확인창)는 완성됐고, 지금은 404 를 받으면 "아직 지원되지 않는 기능입니다"
로 안내한다. **배포되면 프론트 변경 0 으로 동작한다**(404 판정만 사라짐). UI v2 수락 기준 19개 중
**유일한 미충족이 이것**이다.

## 3. 🟠 §35 — 방문 단위 메모, 방문 사진 삭제

명세 v2 는 메모·사진을 **방문 단위**로 쓰고 고친다(체크인·방문 수정). 사진은 `POST /api/visits/:id/photos`
로 이미 된다. 메모는 안 된다.

**실측**

| 호출 | 결과 |
|---|---|
| `POST /api/visits/:id/memos` · `/memos/text` | 라우트 없음 — 그런데 **OpenAPI 에는 `/memos/text` 가 남아 있다** |
| `DELETE /api/visits/:id/photos/:attachmentId` | 라우트 없음 |
| `PATCH /api/fields/:id/memos/:memoId` | 라우트 없음 (수정 = 삭제 + 재생성만 가능) |
| `GET /api/fields/:id` 의 `photos[]` | 현장 직접 첨부만. 방문 사진 0건 |

**요청**
1. 방문 텍스트 메모: `POST /api/visits/:id/memos` + `PATCH`/`DELETE`. 또는 기존 메모 테이블에 `visit_id`
   nullable FK 를 달아 현장 메모 API 에 `visitId` 를 받는 방식도 좋다 — 편한 쪽으로 정하고 알려 달라.
2. 방문 사진 삭제: `DELETE /api/visits/:id/photos/:attachmentId` → 204.
3. `GET /api/fields/:id` 에 방문 사진·메모를 최신순으로 합쳐 내려주기 — 각 항목에 `visitId`·`visitedAt`.
4. OpenAPI 의 `/memos/text`(음성 메모 시절 잔재) 기재 정리.

**프론트 현황 (우회 중)**
- 메모는 **현장 메모 API** 로 쓰고, "방문 시각부터 24시간 안에 쓴 가장 최근 메모"를 그 방문의 메모로 간주한다.
  같은 현장을 하루 두 번 방문하면 구분하지 못한다. 수정은 삭제 + 재생성.
- 방문 수정 화면에서 사진 **제거 버튼은 숨겨 뒀다.**
- 현장 상세 사진은 최근 방문마다 방문 상세를 따로 불러 합친다(N+1 호출).
- 서버가 붙으면 메모 연결 판정(`memoForVisit`) 한 곳을 바꾸고, 사진 제거 버튼을 다시 노출하고, 현장 상세의
  N+1 합치기를 걷어내면 된다.

## 4. 🟠 §40 — 방문 이력이 있는 현장은 영원히 삭제할 수 없다

**실측**: 방문이 1건이라도 있으면 `DELETE /api/fields/:id` → **409 `has_related_visits`** `{visitCount}`.
현장을 한 번이라도 방문하면 사용자가 정리할 방법이 없다.

명세 v2 는 반대다: 현장을 지워도 **과거 방문은 외근 내역·외근 정리·보고서에서 삭제 시점의 현장 정보로
계속 보인다.** 삭제를 막는 조건은 "**진행 중 외근**에 포함된 현장" 하나뿐이다.

**요청**
1. 현장 soft delete 를 방문 이력과 무관하게 허용. 삭제 후에도 과거 외근·방문·보고서 응답의 현장명·주소는 채워 줄 것.
2. 진행 중 외근의 목적지인 현장만 409 `field_in_active_trip`.

**프론트 현황**: 진행 중 외근 목적지면 먼저 막고("외근 종료 후 삭제할 수 있습니다"), `has_related_visits` 는
"방문 기록이 있는 현장은 아직 삭제할 수 없습니다" 로 안내한다. 배포되면 두 번째 안내가 자연히 사라진다.

## 5. 🟠 §30-B — 위치정보 이용약관 페이지 · 약관 본문 교체 (이월)

7/29 전달본의 마지막 미결 항목이다. **2026-10-01 그대로**:

- `/location-terms` → 404.
- `/terms`·`/privacy` → 시행일 **`2026-06-18`** 구 초안. '위치정보' 문구 0회.
- 반면 `GET /api/me` 의 `legal.current` 는 이미 `2026-08-03` → 그래서 **전 사용자 `needsReaccept: true`**.

이것이 막고 있는 것: 가입 화면 '위치정보 이용약관' 링크(지금은 일반 약관으로 대체), 재동의 배너,
동의 버전 기록의 정확성, **Play 프로덕션 승격.** 프론트는 `utils/contact.ts` 의 `LEGAL_DOCS` 한 곳만
올리면 세 가지가 함께 풀린다.

**요청**: 확정 본문(v1.0, 시행일 2026-08-03) 3종을 배포하고 알려 달라.

## 6. 🟠 §31-B — Word 결과물 `/output/*.docx` 서빙 라우트 없음 (이월)

`GET /api/reports` 가 `outputFileUrl: "/output/report-….docx"` 를 내려주는데 그 경로는 라우트가 없다
(2026-10-01 재확인, Express 기본 404 171 B). 보고서 화면의 Word 다운로드가 실패한다. PDF 는 정상.

**요청**: `/output` 정적 서빙 추가, 또는 Word 를 파일 스토리지(`/storage/reports/…`)로 옮겨 경로를 하나로.

**덤(사소)**: `/storage/*` 200 응답에 `Content-Type` 헤더가 없다. 증상은 없지만 `image/jpeg` 를 붙여 달라.

## 7. 🟡 §37 — `기타` 결과의 사유 10자 강제

명세 v2: 체크인·방문 수정의 입력은 **전부 선택**이다. 서버는 `PATCH /api/visits/:id/status {status:"other"}`
에 사유가 10자 미만이면 400 `visit_status_reason_required`.

**요청**: `reason` 을 선택으로. 10자 규칙에 근거가 있으면 알려 달라 — 프론트는 근거 문서를 찾지 못했다.
지금은 프론트가 저장 전에 10자 미만을 막고 안내한다.

## 8. 🟡 §39 — 현장 보고에 `visitId` 가 없다

"보고서에 쓰인 방문은 삭제 차단"을 판정하려면 현장 보고가 어느 방문에서 왔는지 알아야 한다.

**요청**: `field_reports.visit_id`(nullable). 2번의 409 `visit_in_report` 를 서버가 판정해 주면 이 컬럼이
응답에 없어도 된다. 프론트는 지금 "같은 외근 보고서에 같은 현장의 현장 보고가 있으면 차단"으로 근사한다.

## 9. 🟡 §29 — 보고서 목록 item 에 외근 요약

`GET /api/reports` item 에 `tripId` 만 있다(18/18). 목록은 외근 날짜로 묶는데, 오래된 외근은 로컬에 없어
'외근 정보 미로드' 그룹으로 빠진다.

**요청**: 상세(`GET /api/reports/:id`)가 이미 주는 요약을 목록에도 — `"trip": { "tripDate", "startedAt", "endedAt" }`.

---

## 10. 🟡 §32 — 주소검색 `roadAddress` 가 `null` 로 온다

`keyword=하단동` 10건 중 3건(동 단위 결과)이 `roadAddress: null`. 스키마는 `string`.
**요청**: 스키마를 `string | null` 로 고치거나 빈 문자열로 보내기. 프론트는 경계에서 정규화해 앱은 안전하다.

---

## 11. 🟢 §38 — `from-trip` 의 `fieldIds`·순서 (선택)

`POST /api/reports/from-trip/:tripId` 가 `fieldIds` 를 무시한다. 프론트는 빈 보고서 + 현장 보고 순차 생성으로
우회했고(생성 순 = 조회 순), 명세는 이미 충족한다. 있으면 좋은 것: `fieldIds[]`(순서 포함), `FieldReport.order`.
