## 1. 🔴 `DELETE /api/me` — 앱 내 회원 탈퇴 (출시 차단)

### 배경

**출시 대상은 Google Play 뿐이다** (App Store 는 계획에 없음). Play 는 계정 생성을 허용하는 앱에
**계정·데이터 삭제 경로를 요구**하며 데이터 안전 양식 기재 대상이다. 현재는 운영팀 이메일 수동
처리라 **처리방침이 말하는 절차와 실제 서비스가 어긋난다.**

### 실측 (2026-07-29, 운영 OpenAPI + 무인증 프로브)

| 요청 | 결과 |
|---|---|
| `GET /api/me` | 401 — 라우트 존재 |
| `PATCH /api/me` | 401 — 라우트 존재 |
| **`DELETE /api/me`** | **404** |
| `DELETE /api/zzz-nonexistent` | 404 — 위와 동일 |

`api-docs.json` 전체에 사용자 삭제 엔드포인트가 **0건**이다.

### 프론트엔드 상태 (2026-07-29 머지, `c577c31`)

- `auth.deleteMe()` — `DELETE /api/me`, body `{ password }`
- `authStore.deleteAccount()` — 성공 시에만 로컬 세션 정리
- `app/(tabs)/profile/delete-account.tsx` — 안내·비밀번호·동의 체크·최종 확인
- **미구현을 성공으로 위장하지 않는다**: 404/405/501 이면 로컬 세션을 **지우지 않고** 실패 안내 +
  메일 문의 경로를 준다. 로컬만 비우면 사용자는 탈퇴됐다고 믿고 떠나는데 계정은 서버에 남는다
- `user_not_found` 만 예외로 '이미 삭제됨' 으로 보고 로컬 정리

### 백엔드가 해야 할 것

```
DELETE /api/me
Authorization: Bearer <accessToken>
Body: { "password": "..." }     ← 재인증을 요구한다면
```

계약에서 **못박아 달라**:

1. **재인증 수단** — 비밀번호인지, refresh 토큰인지, access 토큰만으로 충분한지.
   프론트는 일단 `{ password }` 를 싣는다(서버가 무시해도 무해).
2. **삭제 범위** — 회원 기본정보·외근기록·방문기록·업무보고·**사진(스토리지 객체 포함)**·메모·
   세션/토큰. DB row 만 지우고 MinIO 객체가 남으면 개인정보가 남는 것이다.
3. **성공 응답** — 204 인지 `{ deleted: true }` 인지. 프론트는 둘 다 받도록 열어 뒀다.
4. **동일 이메일 재가입 허용 여부** — soft delete 라면 재가입이 `email_already_exists` 로 막히는지.
5. **법령상 보관 대상** — 별도 보관한다면 무엇을 얼마나. 화면에 고지 문구를 띄워 뒀으므로
   실제 정책과 맞춰야 한다.

### 검증 케이스

- 정상 탈퇴 → 이후 같은 토큰으로 `GET /api/me` 401
- 비밀번호 불일치 → `current_password_invalid` (또는 합의된 code) 400/401
- 이미 삭제된 계정 → `user_not_found`
- 사진이 있는 계정 삭제 → **스토리지 객체까지 사라졌는지 직접 확인**
- 진행 중 외근이 있는 계정 — 거부할지 함께 지울지 정책 필요

### ⚠️ 확인 필요 — 삭제 요청 **웹 URL**

Play 는 앱 내 삭제 경로와 별개로 **앱 밖에서 접근 가능한 삭제 요청 URL** 도 요구하는 것으로
알려져 있다(데이터 안전 양식 기재). 앱을 설치하지 않은 사람도 삭제를 요청할 수 있어야 한다는
취지다.

**Play Console 데이터 안전 양식에서 실제 문항을 확인해 달라.** 필요하다면 §2 의 정책 페이지에
`/account-deletion` 같은 페이지가 한 건 더 붙는다 — 삭제 대상·절차·문의처를 안내하는 정적
페이지면 충분할 가능성이 높다.

> 정책 판단이라 여기서 단정하지 않는다. 다만 **필요한 것으로 밝혀지면 백엔드 작업이 늘어나므로**
> 일찍 확인하는 편이 낫다.

## 2. 🔴 정책 페이지 — `/location-terms` 신설 + 본문 교체

### 배경

약관 3종이 **이미 확정본으로 작성돼 있다** (Notion 「📄 이용약관 (조성민)」, v1.0, 시행일 2026-08-03).
그런데 서버는 `/terms`·`/privacy` 를 **구 초안**으로 서빙 중이고, **위치정보 이용약관은 페이지 자체가
없다**.

### 실측 (2026-07-29)

| 경로 | 상태 |
|---|---|
| `GET /terms` | 200 · 1,062자 — **구 초안** |
| `GET /privacy` | 200 · 1,241자 — **구 초안** |
| `GET /location-terms` | **404** (`/location`·`/terms/location` 도 404) |
| `/terms`·`/privacy` 본문의 '위치정보' 언급 | **없음** |

지금 **가입 화면은 위치정보 이용약관을 필수 동의 3종으로 받으면서 링크는 일반 `/terms` 를 가리킨다**
(`app/(auth)/signup.tsx:40`). 동의받는 문서와 보여주는 문서가 다르다.

### 정본 위치 — repo 로 관리

문서 원본을 **백엔드 repo** 에 둔다. 노션은 작성 도구로만 쓴다.

```
docs/legal/
├── terms.md
├── privacy.md
└── location-terms.md
```

- 각 파일 **상단에 `시행일: 2026-08-03`**, **하단에 `개정 이력`** 섹션
- **문서당 파일 하나, 항상 현행.** 과거 본문은 git 이력에서 꺼낸다
  (`git show <commit>:docs/legal/terms.md`). 개정 시 태그 `legal-YYYY-MM-DD`
- **약관 개정에 앱 빌드가 끼면 안 된다** — 백엔드 배포 하나로 반영되는 게 이 배치의 목적이다

### 백엔드가 해야 할 것

1. `docs/legal/` 3파일 커밋 (본문은 팀이 노션에서 확정 후 전달)
2. **`GET /location-terms` 라우트 추가**
3. `/terms`·`/privacy` 를 v1.0 본문으로 교체

### 검증 케이스

- 세 URL 모두 **로그인 없이** 200
- 셋이 **서로 다른 본문**을 반환 (지금은 위치정보가 `/terms` 와 같은 문서로 취급됨)
- 본문에 시행일 `2026-08-03` 표기

### 프론트 대응 (페이지 뜨는 즉시, 두 줄)

- `src/utils/contact.ts` — `LOCATION_TERMS_AVAILABLE = true`
- `app/(auth)/signup.tsx:40` — `location` 링크를 `/location-terms` 로

> 지금은 프로필 메뉴에 위치정보 약관을 **일부러 노출하지 않고 있다.** 페이지가 뜨면 켠다.

## 3. 🟠 약관 동의 **버전** 기록 (소급 불가)

### 배경

가입 요청이 약관 동의를 **`termsAgreed: true` 불리언 하나**로 보낸다. 화면에서는 이용약관·처리방침·
위치정보약관을 **각각 체크**받는데, 서버에는 "동의했다" 만 남는다. **어느 문서의 어느 버전에
동의했는지 알 방법이 없다.**

약관은 반드시 개정된다. 그때 "기존 사용자에게 재동의를 받아야 하는가" 를 판단하려면 이 데이터가
필요한데, **소급 생성이 불가능하다.** 지금 가입하는 사용자마다 버전 없는 기록이 쌓인다.

### 백엔드가 해야 할 것

기존 필드를 유지하고 optional 로 얹는다(구버전 앱 호환):

```jsonc
// POST /auth/signup
{
  "termsAgreed": true,              // 유지
  "agreedTerms": {                  // 신규 (optional)
    "service":  "2026-08-03",
    "privacy":  "2026-08-03",
    "location": "2026-08-03"
  }
}
```

- 버전 식별자는 **시행일 `YYYY-MM-DD`**. 문서 상단 표기와 같은 값이라 사람이 대조하기 쉽다.
- 저장은 사용자당 1행이 아니라 **(사용자 × 문서 × 버전) 이력**으로 쌓여야 한다.
  **재동의 시 행이 추가돼야지 덮어써지면 안 된다.**
- **`GET /api/me` 응답에 현재 동의 버전 포함** — 앱이 "개정됐으니 재동의" 배너를 띄울 수 있다.

### 검증 케이스

- `agreedTerms` 없이 가입(구버전 앱) → 기존대로 성공, 버전은 null
- 같은 사용자가 재동의 → 행이 **추가**되고 이전 행이 남아 있는지
- `GET /api/me` 로 방금 동의한 버전이 읽히는지

### 프론트 상태

**미배선.** 시행일이 확정됐으므로 착수 가능하다. 계약이 정해지면 `SignupBody.agreedTerms?` 를
optional 로 추가한다.

> 프론트가 일부러 선반영하지 않았던 이유: 시행일이 없는 상태에서 버전 문자열을 지어내면
> **사실이 아닌 동의 이력**이 쌓인다. 기록이 없는 것보다 나쁘다.

## 4. 🟠 보관기간 **30일** — 실제로 지켜지는가 (확인 먼저)

### 배경

확정된 약관이 보관기간을 명시한다.

| 문서 | 조항 | 선언 |
|---|---|---|
| 개인정보처리방침 | §4 | 외근기록·위치기록 **외근 종료 후 30일**, 접속·오류 로그 최대 6개월 |
| 위치정보 이용약관 | §7 | 현재 위치·이동 경로·위치 기록 **외근 종료 후 30일** |

**먼저 알려 달라 — 30일 경과분을 파기하는 배치가 실재하는가?** 프론트에서는 확인할 수 없다.

### 없다면 둘 중 하나

1. **삭제 배치 구현** — 외근 종료 시각 기준 30일 경과분 파기.
   파기 대상에 **스토리지 객체(MinIO)** 포함. DB row 만 지우면 파기한 게 아니다.
2. **문서를 실제에 맞게 수정** — 팀이 본문을 고친다.

### 판단 재료

- 앱에서 보고서·외근 이력은 현재 **기한 없이 조회된다.** 30일 파기가 실제로 돌면
  **오래된 보고서가 사라지는 UX 변화**가 생긴다 — 문서를 고치는 쪽으로 기울 이유가 될 수 있다.
- 결정 전에 **"무엇을 30일로 볼 것인가"** 를 좁히는 게 낫다. 위치 좌표만인지, 외근 기록 전체인지,
  보고서까지인지에 따라 영향이 완전히 달라진다.

**8/3 시행 전에 정해져야 한다.** 지키지 못할 보관기간을 공개 문서로 선언하는 것은 단순 문구
불일치보다 무겁다.

## 5. 🟢 비밀번호 재설정 SMTP (낮음)

`POST /auth/password/reset-request` 는 존재하지만 OpenAPI 설명이 **"(스텁) SMTP·토큰 저장은
미구현. 항상 `{ ok: true }` 만 반환"** 이다. 그래서 프론트는 **배선하지 않고** 로그인 화면의 수동
안내를 유지한다 — 현재 문구가 사실과 맞다.

실제로 메일이 나가게 되면 알려 달라. 그때 로그인 화면 안내를 자동 플로우로 바꾼다.

## 부록 B. 문서와 앱이 어긋난 지점 (참고 — 문서 수정은 팀 진행 중)

백엔드 작업은 아니지만, 심사 대응 맥락에서 공유한다. **앱이 안 하는 걸 문서가 한다고 적은**
방향의 불일치다.

| 문서가 말하는 것 | 앱의 실제 |
|---|---|
| **백그라운드 위치 수집** — 이용약관 §6, 위치정보약관 §5, 처리방침 §2④ | 백그라운드 권한을 **요청하지 않는다**. 포그라운드 전용. 앱 내 안내 문구는 **"백그라운드 위치는 수집하지 않습니다."** |
| **관리자 역할·열람** — 이용약관 §3·§7, 위치정보약관 §2④·§9, 처리방침 §3 | **관리자 개념이 없다** (단일 Actor). 관리자 화면도 접근 기록 저장도 없다 |
| **이동 경로 기록** | 위치 조회는 단발성. 경로는 카카오모빌리티가 계산한 **예상 경로**지 실제 궤적이 아니다 |
| **가입 시 기관명·부서·직급 수집** — 처리방침 §2① | `SignupBody` 는 `email`·`password`·`name` 뿐 |

> ⚠️ **§4(30일 보관)와 이 표의 "관리자 접근 기록 저장" 은 백엔드 확인이 필요하다.**
> 나머지는 문서를 고치는 방향이 맞다 — 특히 백그라운드 위치는 Play 심사에서 가장 까다로운
> 권한이라, 실제로 안 쓰는 걸 선언하면 심사만 어려워지고 얻는 게 없다.
