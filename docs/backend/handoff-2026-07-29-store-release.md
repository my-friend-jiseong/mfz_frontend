## 1. 🔴 `DELETE /api/me` — 앱 내 회원 탈퇴 (출시 차단)

### 배경

**출시 대상은 Google Play 뿐이다** (App Store 는 계획에 없음). Play 는 계정 생성을 허용하는 앱에
**계정·데이터 삭제 경로를 요구**하며 데이터 안전 양식 기재 대상이다. 현재는 운영팀 이메일 수동
처리라 **처리방침이 말하는 절차와 실제 서비스가 어긋난다.**

### 실측 (2026-07-29, 운영 OpenAPI + 무인증 프로브)

| 요청 | 결과 |
|---|---|
| `GET /api/me` | 401 — 라우트 존재 |
| `PATCH /api/me` | 401 — 라우트 존재 |
| **`DELETE /api/me`** | **404** |
| `DELETE /api/zzz-nonexistent` | 404 — 위와 동일 |

`api-docs.json` 전체에 사용자 삭제 엔드포인트가 **0건**이다.

**소스 확인**: DELETE 라우트는 7개(`categories/:id`, `fields/:id`, `fields/:id/memos/:memoId`,
`fields/:id/photos/:photoId`, `trips/:tripId`, `reports/:reportId`,
`reports/:reportId/field-reports/:id`) — **사용자 삭제는 없다.**

> ✅ **좋은 소식**: `prisma/schema.prisma` 의 `User` 에 **`deletedAt DateTime?` 컬럼이 이미 있다.**
> soft delete 로 갈 거면 스키마 마이그레이션 없이 시작할 수 있다.

### 프론트엔드 상태 (2026-07-29 머지, `c577c31`)

- `auth.deleteMe()` — `DELETE /api/me`, body `{ password }`
- `authStore.deleteAccount()` — 성공 시에만 로컬 세션 정리
- `app/(tabs)/profile/delete-account.tsx` — 안내·비밀번호·동의 체크·최종 확인
- **미구현을 성공으로 위장하지 않는다**: 404/405/501 이면 로컬 세션을 **지우지 않고** 실패 안내 +
  메일 문의 경로를 준다. 로컬만 비우면 사용자는 탈퇴됐다고 믿고 떠나는데 계정은 서버에 남는다
- `user_not_found` 만 예외로 '이미 삭제됨' 으로 보고 로컬 정리

### 백엔드가 해야 할 것

```
DELETE /api/me
Authorization: Bearer <accessToken>
Body: { "password": "..." }     ← 재인증을 요구한다면
```

계약에서 **못박아 달라**:

1. **재인증 수단** — 비밀번호인지, refresh 토큰인지, access 토큰만으로 충분한지.
   프론트는 일단 `{ password }` 를 싣는다(서버가 무시해도 무해).
2. **삭제 범위** — 회원 기본정보·외근기록·방문기록·업무보고·**사진(스토리지 객체 포함)**·메모·
   세션/토큰. DB row 만 지우고 MinIO 객체가 남으면 개인정보가 남는 것이다.
3. **성공 응답** — 204 인지 `{ deleted: true }` 인지. 프론트는 둘 다 받도록 열어 뒀다.
4. **동일 이메일 재가입 허용 여부** — soft delete 라면 재가입이 `email_already_exists` 로 막히는지.
5. **법령상 보관 대상** — 별도 보관한다면 무엇을 얼마나. 화면에 고지 문구를 띄워 뒀으므로
   실제 정책과 맞춰야 한다.

### 검증 케이스

- 정상 탈퇴 → 이후 같은 토큰으로 `GET /api/me` 401
- 비밀번호 불일치 → **`current_password_invalid`** (`PATCH /api/me/password` 와 같은 code).
  프론트가 이 code 로 분기해 비밀번호 입력 옆에 인라인 에러를 붙인다 — 다른 code 를 쓸 거면
  알려 달라. `invalid_credentials` 도 같은 처리로 받아 둔다
- 이미 삭제된 계정 → **`user_not_found`**. 프론트는 이 code 만 '이미 삭제됨' 으로 보고
  로컬 세션을 정리한다(그 외 4xx 는 세션을 유지한다)
- 사진이 있는 계정 삭제 → **스토리지 객체까지 사라졌는지 직접 확인**
- 진행 중 외근이 있는 계정 — 거부할지 함께 지울지 정책 필요

### ⚠️ 확인 필요 — 삭제 요청 **웹 URL**

Play 는 앱 내 삭제 경로와 별개로 **앱 밖에서 접근 가능한 삭제 요청 URL** 도 요구하는 것으로
알려져 있다(데이터 안전 양식 기재). 앱을 설치하지 않은 사람도 삭제를 요청할 수 있어야 한다는
취지다.

**Play Console 데이터 안전 양식에서 실제 문항을 확인해 달라.** 필요하다면 항목 2 의 정책 페이지에
`/account-deletion` 같은 페이지가 한 건 더 붙는다 — 삭제 대상·절차·문의처를 안내하는 정적
페이지면 충분할 가능성이 높다.

> 정책 판단이라 여기서 단정하지 않는다. 다만 **필요한 것으로 밝혀지면 백엔드 작업이 늘어나므로**
> 일찍 확인하는 편이 낫다.

## 2. 🔴 정책 페이지 — `/location-terms` 신설 + 본문 교체

### 배경

약관 3종이 **이미 확정본으로 작성돼 있다** (Notion 「📄 이용약관 (조성민)」, v1.0, 시행일 2026-08-03).
그런데 서버는 `/terms`·`/privacy` 를 **구 초안**으로 서빙 중이고, **위치정보 이용약관은 페이지 자체가
없다**.

### 실측 (2026-07-29)

| 경로 | 상태 |
|---|---|
| `GET /terms` | 200 · 1,062자 — **구 초안** |
| `GET /privacy` | 200 · 1,241자 — **구 초안** |
| `GET /location-terms` | **404** (`/location`·`/terms/location` 도 404) |
| `/terms`·`/privacy` 본문의 '위치정보' 언급 | **없음** |

**소스 확인 — 현재 서빙 방식이 이번 작업의 실제 범위를 바꾼다.**

두 페이지는 [`src/legal/registerLegalRoutes.js`](../../../mfz_backend/src/legal/registerLegalRoutes.js) 안에
**`PRIVACY_HTML`·`TERMS_HTML` 템플릿 리터럴로 하드코딩**돼 있고 `app.get` 이 그대로 `send` 한다.
파일에서 읽지 않는다. 그래서 아래 두 가지가 **드러나 있다**:

- 서빙 중인 본문의 시행일이 **`2026-06-18`** — 새 약관(`2026-08-03`)과 다르다.
- 본문 문의처가 **`support@ilgayo.co.kr`** — **폐기하기로 한 주소**가 지금 공개 페이지에 떠 있다(부록 A).
- 처리방침 §6 이 "계정 삭제는 **앱 내 문의 또는 운영자 연락처로 요청**" 이라고 적고 있다 —
  항목 1 이 해결되면 이 문장도 함께 바뀌어야 한다.

지금 **가입 화면은 위치정보 이용약관을 필수 동의 3종으로 받으면서 링크는 일반 `/terms` 를 가리킨다**
(`app/(auth)/signup.tsx:40`). 동의받는 문서와 보여주는 문서가 다르다.

### 정본 위치 — repo 로 관리

문서 원본을 **백엔드 repo** 에 둔다. 노션은 작성 도구로만 쓴다.

```
docs/legal/
├── terms.md
├── privacy.md
└── location-terms.md
```

- 각 파일 **상단에 `시행일: 2026-08-03`**, **하단에 `개정 이력`** 섹션
- **문서당 파일 하나, 항상 현행.** 과거 본문은 git 이력에서 꺼낸다
  (`git show <commit>:docs/legal/terms.md`). 개정 시 태그 `legal-YYYY-MM-DD`
- **약관 개정에 앱 빌드가 끼면 안 된다** — 백엔드 배포 하나로 반영되는 게 이 배치의 목적이다

### 백엔드가 해야 할 것

1. **서빙 구조 전환** — 하드코딩 HTML 문자열 → `docs/legal/*.md` 파일 읽기.
   md→html 렌더를 붙이든, 빌드 시 변환하든 방식은 맡긴다. **이게 이번 항목의 실제 작업량이다**
   (문서 3개를 넣는 것보다 이 전환이 크다).
2. `docs/legal/` 3파일 커밋 (본문은 팀이 노션에서 확정 후 전달)
3. **`GET /location-terms` 라우트 추가**
4. `/terms`·`/privacy` 를 v1.0 본문으로 교체 — 시행일·문의처가 함께 갱신된다

> 전환이 부담이면 **하드코딩을 유지한 채 본문만 교체해도 8/3 은 넘긴다.** 다만 그러면 약관

### 검증 케이스

- 세 URL 모두 **로그인 없이** 200
- 셋이 **서로 다른 본문**을 반환 (지금은 위치정보가 `/terms` 와 같은 문서로 취급됨)
- 본문에 시행일 `2026-08-03` 표기

### 프론트 대응 (배포 즉시)

## 3. 🟠 약관 동의 **버전** 기록 (소급 불가)

### 배경

가입 요청이 약관 동의를 **`termsAgreed: true` 불리언 하나**로 보낸다. 화면에서는 이용약관·처리방침·
위치정보약관을 **각각 체크**받는데, 서버에는 "동의했다" 만 남는다. **어느 문서의 어느 버전에
동의했는지 알 방법이 없다.**

약관은 반드시 개정된다. 그때 "기존 사용자에게 재동의를 받아야 하는가" 를 판단하려면 이 데이터가
필요한데, **소급 생성이 불가능하다.** 지금 가입하는 사용자마다 버전 없는 기록이 쌓인다.

**소스 확인**: `src/auth/sessionService.js:188` 이 `termsAgreed !== true` 면 `terms_required` 로
거부할 뿐 **저장하지 않는다.** `prisma/schema.prisma` 의 `User` 에 동의 관련 컬럼이 없고,
동의 이력 테이블도 없다. 즉 **지금 동의 기록은 어디에도 남지 않는다** — 버전 이전에 동의
사실 자체가 없다.

### 백엔드가 해야 할 것

기존 필드를 유지하고 optional 로 얹는다(구버전 앱 호환):

```jsonc
// POST /auth/signup — 프론트가 지금 실제로 보내는 형태
{
  "termsAgreed": true,              // 유지
  "agreedTerms": {                  // 신규 (optional)
    "service":  "2026-06-18",
    "privacy":  "2026-06-18"
    // "location" 은 아직 없음 — 항목 2 참조
  }
}
```

- 버전 식별자는 **시행일 `YYYY-MM-DD`**. 문서 상단 표기와 같은 값이라 사람이 대조하기 쉽다.

> ⚠️ **값이 `2026-08-03` 이 아닌 이유 — 의도된 것이다.**
> 이 값은 **그 시점에 실제로 서빙되던 본문의 시행일**이다. 지금 `/terms`·`/privacy` 는 구 초안
> (`2026-06-18`)을 서빙하고 있으므로, 오늘 가입하는 사용자는 그 문서를 보고 동의한 것이다.
> 아직 배포되지 않은 `2026-08-03` 을 미리 적으면 **사실이 아닌 동의 이력**이 된다.
> `location` 키가 빠진 것도 같은 이유다 — 페이지가 없어 사용자가 본 적이 없다.
>
> **항목 2 에서 새 본문을 배포할 때 프론트 상수(`src/utils/contact.ts` 의 `LEGAL_DOCS`)를
> 같이 올린다.** 그 이후 가입자부터 `2026-08-03` 으로 기록된다. 스키마는 **어떤 날짜 문자열이든
> 받을 수 있게** 해 달라 — 특정 값을 고정하지 말 것.
- 저장은 사용자당 1행이 아니라 **(사용자 × 문서 × 버전) 이력**으로 쌓여야 한다.
  **재동의 시 행이 추가돼야지 덮어써지면 안 된다.**
- **`GET /api/me` 응답에 현재 동의 버전 포함** — 앱이 "개정됐으니 재동의" 배너를 띄울 수 있다.

> **재동의 정책(개정 시 전체 재동의 vs 통지만)은 아직 미정이다.** 다만 위처럼 **이력으로 쌓아
> 두면 어느 쪽으로 정해지든 대응된다** — 덮어쓰기로 만들면 그때 되돌릴 수 없다. 그래서
> 정책 결정을 기다리지 말고 이력 구조로 진행해 달라.

### 검증 케이스

- `agreedTerms` 없이 가입(구버전 앱) → 기존대로 성공, 버전은 null
- 같은 사용자가 재동의 → 행이 **추가**되고 이전 행이 남아 있는지
- `GET /api/me` 로 방금 동의한 버전이 읽히는지

### 프론트 상태 — ✅ **배선 완료** (2026-07-29)

- `src/utils/contact.ts` `LEGAL_DOCS` — 문서별 URL + **현재 배포된 시행일**을 한 곳에 둔다.
  `LOCATION_TERMS_AVAILABLE` 도 여기서 파생시켰다(따로 관리하면 페이지는 떴는데 메뉴가
  꺼진 채로 남는다).
- `agreedTermsPayload()` — **배포된 문서만** 싣고, 전부 미배포면 필드 자체를 뺀다.
- `SignupBody.agreedTerms?` 로 가입 요청에 실린다. **서버가 무시해도 무해**하다
  (`handleSignup` 이 필드를 골라 읽는 구조 — 소스 확인).
- 단위 테스트 5건으로 "미배포 문서는 절대 실리지 않는다" 를 고정했다
  (`src/utils/__tests__/contact.test.ts`).

**그래서 지금 서버를 붙이면 바로 기록이 쌓인다.** 프론트 추가 작업 없음.

## 4. 🔴 보관기간 **30일** — 파기 배치가 **없다** (확인 완료)

### 배경

확정된 약관이 보관기간을 명시한다.

| 문서 | 조항 | 선언 |
|---|---|---|
| 개인정보처리방침 | §4 | 외근기록·위치기록 **외근 종료 후 30일**, 접속·오류 로그 최대 6개월 |
| 위치정보 이용약관 | §7 | 현재 위치·이동 경로·위치 기록 **외근 종료 후 30일** |

**소스 확인 결과 — 파기 배치가 존재하지 않는다.** `mfz_backend` 전체에 cron·스케줄러·
`setInterval`·retention/cleanup/purge 코드가 **0건**이다. 코드에 나오는 "30일" 은 전부
**조회 기본 필터**(`GET /api/trips` 의 `visited_at` 최근 30일 기본값)이지 파기가 아니다.
`scripts/` 에도 파기 스크립트가 없다.

### ✅ 결정 (2026-07-29) — 배치를 만들지 않고 **문서를 고친다**

배치를 도는 쪽은 부작용이 크다. 앱에서 보고서·외근 이력은 현재 기한 없이 조회되므로,
30일 파기가 실제로 돌면 **사용자의 오래된 보고서가 사라지는 UX 변화**가 된다.
**백엔드에 구현 작업은 없다.**

### 다만 — 이 결정은 30일 두 줄보다 넓다

처리방침 §4 의 보관기간 표는 5행인데, 소스 확인 결과 **4행이 관리되지 않고 있다.**

| 처리방침 §4 항목 | 선언 | 실제 |
|---|---|---|
| 회원정보 | 회원 탈퇴 시까지 | ✅ 맞다 — 단 **탈퇴가 항목 1 대기** |
| 외근기록 | 외근 종료 후 30일 | ❌ 파기 없음 |
| 위치기록 | 외근 종료 후 30일 | ❌ 파기 없음 |
| 접속로그 | 최대 6개월 | ❌ **로거·nginx 로그 설정이 repo 에 없다** — 컨테이너 로그 기본 정책에 맡겨져 있다 |
| 오류로그 | 최대 6개월 | ❌ 동일 (백엔드에 Sentry·winston·pino 류 0건) |

위치정보약관 §7(현재 위치·이동 경로·위치 기록 30일)도 같은 상태다.
**문서를 고칠 때 30일 두 줄만 손대면 나머지가 그대로 남는다.**

### 백엔드가 해야 할 것 — 답변 하나

구현은 없다. 대신 팀이 문서를 **정확하게** 고칠 수 있도록 아래를 알려 달라.

1. **접속·오류 로그가 실제로 어디에 얼마나 남는가** — 컨테이너 로그 드라이버 설정,
   호스트 logrotate, 보존 일수. "설정한 적 없다" 도 유효한 답이다.
2. **백업 보관 주기** — 두 문서 모두 "백업 데이터는 복구 목적의 제한된 기간 후 삭제" 라고
   적었는데, 실제 백업 정책이 있는지.
3. 항목 1 이 붙으면 회원 탈퇴 시 **무엇이 즉시 지워지고 무엇이 남는지** (스토리지 객체 포함).

> 이 답이 있어야 "탈퇴 시까지 보관" 이라고 쓸지 다른 표현을 쓸지 정할 수 있다.
> 지키지 못할 보관기간을 공개 문서로 선언하는 건 단순 문구 불일치보다 무겁다 —
> **고치는 쪽으로 정한 이상 실제와 맞는 문장이어야 의미가 있다.**

## 5. 🟢 비밀번호 재설정 SMTP (낮음)

`POST /auth/password/reset-request` 는 존재하지만 OpenAPI 설명이 **"(스텁) SMTP·토큰 저장은
미구현. 항상 `{ ok: true }` 만 반환"** 이다. 그래서 프론트는 **배선하지 않고** 로그인 화면의 수동
안내를 유지한다 — 현재 문구가 사실과 맞다.

실제로 메일이 나가게 되면 알려 달라. 그때 로그인 화면 안내를 자동 플로우로 바꾼다.

## 부록 B. 문서와 앱이 어긋난 지점 (참고 — 문서 수정은 팀 진행 중)

백엔드 작업은 아니지만, 심사 대응 맥락에서 공유한다. **앱이 안 하는 걸 문서가 한다고 적은**
방향의 불일치다.

| 문서가 말하는 것 | 앱의 실제 |
|---|---|
| **백그라운드 위치 수집** — 이용약관 §6, 위치정보약관 §5, 처리방침 §2④ | 백그라운드 권한을 **요청하지 않는다**. 포그라운드 전용. 앱 내 안내 문구는 **"백그라운드 위치는 수집하지 않습니다."** |
| **관리자 역할·열람** — 이용약관 §3·§7, 위치정보약관 §2④·§9, 처리방침 §3 | `User.role` **컬럼은 있으나**(`@default("user")`) 응답·토큰에 실어 보낼 뿐 **권한 분기에 쓰이지 않는다** — `requireAdmin`/`isAdmin` 류 0건. 관리자 화면도 없다 |
| **관리자 열람 기록 저장** — 위치정보약관 §12, 처리방침 §10 | **audit/access log 가 없다** (소스 확인 0건). 열람 자체가 없으니 기록할 것도 없다 |
| **이동 경로 기록** | 위치 조회는 단발성. 경로는 카카오모빌리티가 계산한 **예상 경로**지 실제 궤적이 아니다 |
| **가입 시 기관명·부서·직급 수집** — 처리방침 §2① | `SignupBody` 는 `email`·`password`·`name` 뿐 |

> **네 줄 모두 소스로 확인했다.** 구현이 없는 쪽이므로 **문서를 고치는 방향이 맞다** —
> 특히 백그라운드 위치는 Play 심사에서 가장 까다로운 권한이라, 실제로 안 쓰는 걸 선언하면
> 심사만 어려워지고 얻는 게 없다. 관리자 조항은 "타인의 위치·이동 경로 열람" 이라는 무거운
> 고지인데 실체가 전혀 없다.
