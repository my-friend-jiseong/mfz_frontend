# 보고서 내보내기 포맷 확장 — PDF · HWP

> **상태**: 확정 (2026-06-06 사용자 결정 — HWP 는 기술 제약으로 HWPX 타깃 권장, 하단)
> **백로그**: PDF = [backend-backlog §19](../backend/backend-backlog.md) (기등재·백엔드 대기) · 위치도 삽입 = §20 · HWP 는 방식 확정 후 등재
> **현황**: Word(docx) 내보내기는 **구현 완료** (`reports.output_file_url`). 이 명세는 그 파이프라인의 포맷 확장.

## 1. PDF (= 백로그 §19, 우선)
- `POST /api/reports/:id/export?format=pdf` — 기존 Word 생성 파이프라인에서 분기 (docx→pdf 변환 또는 직접 렌더).
- 용도: 인쇄·모바일 공유 (Word 는 편집용, PDF 는 제출·열람용).
- §20(위치도 자동 삽입)과 같은 파이프라인에서 처리하면 한 번에.

## 2. HWP — 기술 제약을 전제로 한 선택지

> 보고 대상 기관이 한글 문서를 요구하는 현실 대응. 단 "HWP"는 포맷이 둘이라 타깃을 먼저 정해야 함.

| 선택지 | 내용 | 평가 |
|---|---|---|
| **HWPX 생성 (권장)** | 한컴의 개방 XML 표준(공공기관 통용, zip+XML). 템플릿 기반 서버 생성 가능 — Word(docx=zip+XML) 생성과 같은 접근 | 라이브러리 생태계가 docx 보다 얇아 템플릿 치환 직접 구현 가능성 높음. 현실적 상한선 |
| 구형 HWP(5.0 바이너리) 직접 생성 | 독점 바이너리 포맷 | 사실상 비현실적 — 제외 |
| 한컴 SDK/서버 제품 | 공식 변환·생성 | 유료·계약 — 학생 프로젝트 범위 밖 |
| PDF 로 대체 협의 | 수신 기관이 PDF 허용이면 HWP 자체가 불필요 | **가장 싼 해소** — 실수요 확인 먼저 |

### 권장 순서
1. **PDF(§19) 먼저** — 수요의 대부분을 흡수하는지 실사용 확인
2. HWP 실수요가 확인되면 **HWPX 템플릿 생성**으로 착수 (수신측 한글 버전에서 열리는지 검증 필수)

## 미정 (명세화 필요)
- HWP 실수요 확인 (보고 수신 기관이 정말 HWP 만 받는지 — PDF 허용이면 2번 전체 드롭)
- HWPX 템플릿 레이아웃 (현행 Word 양식과 동일하게 갈지)
- 위치도(§20)·전중후 사진의 HWPX 임베드 방식
